# Data Model

This document describes every table in the MummSTER database, the data sources that feed each one, and the era boundaries and gap years that any analysis needs to respect.

---

## Database Files

Two files, derived from each other:

- **`mummster.db`** — DuckDB. The master. Queries hit this file.
- **`datasette.db`** — SQLite. A subset export, used only by the Datasette viewer.

Both live on the ARTEMIS host at `/mnt/artemis-data/mummster/data/`. Every container that needs read access mounts this directory read-only.

---

## Table Categories

The database contains three kinds of tables:

1. **`sbdb_*` tables** — authoritative, human-curated data from the canonical Excel workbook (`sbdb.xlsx`). Trust these.
2. **`parsed_scores*` tables** — raw extraction from PDF point sheets. Useful for judge-level detail, but coverage is incomplete and confidence is uneven.
3. **Pipeline metadata tables** — OCR results, run logs.

A query interface should default to `sbdb_*` tables for any question about placement, wins, prize counts, captains, themes, or parade history. The `parsed_scores*` tables are for questions specifically about subcategory scoring or judge-level breakdown.

---

## `sbdb_*` Tables (Authoritative)

Imported from `sbdb.xlsx` by `import_sbdb.py` on each pipeline run. Twelve tabs, all prefixed `sbdb_`.

### `sbdb_main_results`
The core competition results table. ~1,960 rows.

| Column            | Notes                                                  |
|-------------------|--------------------------------------------------------|
| Year              | Stored as string (`"2026"`); cast for numeric ops      |
| Band              | Canonical band name (curation-cleaned)                 |
| Place             | Placement; `N`/`DQ`/`WD`/`BD` are non-numeric statuses |
| Total Points      | Final score (era-dependent scale)                      |
| Captain           | Lead captain                                           |
| Theme             | Show theme                                             |
| Designer          | Costume/scenery designer                               |
| Choreographer     | Lead choreographer                                     |
| YouTube           | Video link, if known                                   |
| ... subcategories | Costume, music, performance, etc., when available      |

### `sbdb_hall_of_fame`
~71 rows. Hall of Fame inductees.

### `sbdb_parade_info`
~126 rows, one per parade year going back to 1901. Weather (temp, wind), route, mayor, sponsors, media coverage, total bands, parade-day notes.

### `sbdb_lifetime_achievement`
~24 rows. Lifetime Achievement award recipients.

### `sbdb_custards_last_stand`
~18 rows. Specialty competition winners (Custard's Last Stand is a separate Mummers tradition).

### `sbdb_viewers_choice`
~15 rows. Fan-vote results.

### `sbdb_old_timers_hall_of_fame`, `sbdb_officer_of_the_year`, `sbdb_presidents_award`
Annual recognition awards.

### `sbdb_band_directory`
Contact and roster information for the current bands.

### `sbdb_status_codes`
Legend table mapping placement status codes (`N`, `DQ`, `WD`, `BD`) to definitions. The definitions are filled in via curation.

## `parsed_scores*` Tables (Extraction)

Generated by the pipeline's OCR + parser + vision extractor chain. Cover 1963–2026 but with gaps and uneven accuracy.

### `parsed_scores`
~34,000+ rows. One row per (year, band, category, judge) combination.

| Column            | Notes                                                  |
|-------------------|--------------------------------------------------------|
| year              | Integer                                                |
| band              | As extracted (may have variations from `sbdb_main_results`) |
| category          | Normalized category name (Costume, Music, etc.)        |
| judge             | Judge name or number                                   |
| score             | Numeric                                                |
| confidence        | Extractor confidence, currently flat at 0.50           |
| era               | Era tag (Pre-Modern, Modern, Contemporary)             |
| source_method     | `text` (parse_scores.py) or `vision` (vision_extract.py) |

### `parsed_scores_summary`
~59 rows, one per year covered. Totals and metadata about what was extracted for that year.

### `ocr_results`
Stage-1 OCR output before parsing. Used for debugging extraction failures.

## Era Boundaries

Scoring methodology changed substantially over the decades. Any analysis that compares scores across eras needs to account for this.

| Era            | Years        | Notes                                                |
|----------------|--------------|------------------------------------------------------|
| Pre-Modern     | 1963–1990    | Simpler scoring, fewer categories. Text parser handles these well. |
| Modern         | 1991–2013    | Standardized categories. Both parsers work.          |
| Contemporary   | 2014–2026    | New format, subcategory weighting changed. Vision parser preferred; some Total Score misidentification known. |

Era is denormalized into the `parsed_scores.era` column so queries can filter without doing year-range math every time.

## Gap Years

Years with no parade or no extractable data:

- **2021** — parade cancelled (COVID-19). **MUST be excluded** from every multi-year query, with no exceptions.
- **1964** — no point sheet available. Excluded from `parsed_scores` queries but `sbdb_main_results` has the placement record.
- **1967** — same as 1964.
- **1999** — same.
- **2001** — same.

The pattern: `sbdb_main_results` is the source of truth for placement and basic facts. `parsed_scores` has subcategory detail but only for years where a usable point sheet existed and the extractor succeeded.

### SQL pattern for multi-year queries

```sql
SELECT ...
FROM sbdb_main_results
WHERE CAST(Year AS INTEGER) >= 1981
  AND CAST(Year AS INTEGER) != 2021
  AND Place NOT IN ('N', 'DQ', 'WD', 'BD')
  AND Place IS NOT NULL
```

For `parsed_scores` queries, additionally:

```sql
  AND year NOT IN (1964, 1967, 1999, 2001, 2021)
```

## Band Name Variations

The canonical name lives in `sbdb_main_results.Band`. The same band may appear with variants in other tables — trailing spaces, missing apostrophes, abbreviations. The query interface's system prompt includes the canonical name rules. When in doubt, use `LIKE '%name%'`.

A few known examples:

- "Juniata" (1979–1987) and "Juniata Park" (1988+) are the same band. The 2026 curation merged these into "Juniata Park" across all years.
- "Bobby Gagliardi" and "Bobby Gagliardi " (trailing space) appear as separate entries in some captain queries. Strip whitespace before counting.
- "Uptown" appears with an embedded non-breaking space (`\xa0`) in one 2022 record.

These are tracked in `docs/DATA_QUALITY.md`.

## Subcategory Scoring

The category names that appear in `parsed_scores.category` are normalized by `normalize.py` from raw field names on the point sheets. The standard set:

| Standard name             | Aliases seen on point sheets                                |
|---------------------------|-------------------------------------------------------------|
| Costume                   | COS, Costuming                                              |
| Music Playing             | MP, Music                                                   |
| General Effect Music      | GE Music, GE-M, GEM                                         |
| Visual Performance        | VP, Performance, Production                                 |
| General Effect Visual     | GE Visual, GE-V, GEV                                        |
| Presentation              | Pres, Pres.                                                 |
| Total Score               | Tot, Total, Grand Total, Final                              |
| marching_order            | Position, Order, March #                                    |

Adding a new variation is a one-line dictionary update in `normalize.py`. Both `parse_scores.py` and `vision_extract.py` import from the same dictionary.

## `data_context.md`

A markdown summary file generated at the end of every pipeline run by `generate_context.py`. It contains concrete data examples — recent first-prize winners, top-scoring bands, era summaries, gap years, score distributions — that get injected into the query interface's system prompt.

This is what gives the AI grounded knowledge instead of just an empty schema. When the AI says *"Aqua averaged X points across the contemporary era"*, the era boundaries and band name came from `data_context.md` being in the prompt; only the numeric query result comes from the live SQL execution.

The file is regenerated every pipeline run so it always reflects the current database state.
